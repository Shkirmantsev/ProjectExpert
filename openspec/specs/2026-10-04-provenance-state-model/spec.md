## Requirements
### Requirement: KnowledgeState enum and transition table

The `KnowledgeState` enum MUST support the following values:
`verified`, `inferred`, `assumption`, `conflicting`, `stale`,
`unknown`. The state machine MUST enforce the documented transitions:

- `verified` → `inferred` (LLM-derived evidence; deterministic
  unchanged);
- `inferred` → `stale` (source content changed; old evidence no
  longer matches);
- `stale` → `verified` (re-derived evidence matches the new source
  content);
- `stale` → `unknown` (source deleted; canonical snapshot gone);
- `verified` → `conflicting` (parallel branch reports a different
  authoritative value);
- `inferred` → `unknown` (LLM-disabled; no deterministic evidence
  remains);
- `unknown` → `inferred` (new evidence becomes available).

#### Scenario: verified evidence stays verified when source is unchanged

Given an entity with `KnowledgeState.VERIFIED` and a current source
hash equal to the recorded source hash
When the provenance tracker re-derives the evidence
Then the state stays `verified`.

#### Scenario: verified evidence becomes stale when source changes

Given an entity with `KnowledgeState.VERIFIED` and a recorded source
hash `sha-256:A`
When the current source hash becomes `sha-256:B`
Then the entity transitions to `KnowledgeState.STALE`.

### Requirement: ProvenancePort contract

The platform MUST expose a `ProvenancePort` abstract class in
`pi_platform/ports/runtime/provenance.py` with the following
operations:

- `transition(entity_id: str, *, from_state: KnowledgeState,
  to_state: KnowledgeState, evidence: Mapping[str, object]) ->
  None` — atomic, content-addressed by evidence hash;
- `current_state(entity_id: str) -> Optional[KnowledgeState]`;
- `evidence(entity_id: str) -> Sequence[Evidence]`;
- `staleness_map() -> Mapping[str, KnowledgeState]` — the
  legacy-staleness view used by the freshness tracker.

#### Scenario: transition records the evidence chain

Given an entity `e-1` in state `verified`
When `transition("e-1", from_state="verified", to_state="stale",
evidence={"source_hash_before": "sha-256:A", "source_hash_after":
"sha-256:B"})` runs
Then the entity's state is `stale`
And the evidence chain records the transition with the supplied
metadata.

### Requirement: human vs LLM distinction

The state machine MUST distinguish human / source-derived facts from
LLM-generated interpretations (§54 contract):

- `verified` and `stale` MUST be reachable only from deterministic
  evidence (no `LLM-derived` flag);
- `inferred` MUST carry the `LMA-derived: true` flag so a downstream
  consumer can distinguish the source of the evidence;
- `assumption` MUST carry the `LLM-derived: true` flag and the
  documented `assumed_by` reference;
- `unknown` MUST NOT carry an `LLM-derived` flag (the fact simply
  has no current evidence).

#### Scenario: LLM-derived flag is set on inferred evidence

Given a `Chunk` whose evidence was generated by the Phase 2
`LayeredContextEnricher`'s optional LLM layer
When the chunk is recorded in the provenance tracker
Then the chunk's evidence carries `LLM-derived: true`
And the chunk's state is `inferred`.

### Requirement: staleness map for reconcile

The `ProvenancePort.staleness_map()` operation MUST return the
current state of every tracked entity so the freshness tracker can
replay the staleness delta during reconcile.

#### Scenario: staleness map reflects the post-reconcile state

Given a reconcile that transitioned 10 entities to `stale`
When `staleness_map()` runs after the reconcile
Then the map lists those 10 entities with state `stale`
And the map's entity count equals the reconcile report's
`stale_fact_ids` count.
