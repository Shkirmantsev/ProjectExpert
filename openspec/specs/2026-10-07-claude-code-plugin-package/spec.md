## Requirements


Covers architecture section §42 (Claude Code Plugin
Distribution Profile) and §45 (Plugin Generation
Pipeline). The Claude Code plugin packager emits a
Claude Code plugin package from the canonical Agent
Skill and MCP configuration. The packager is generated,
NOT maintained by hand; the canonical sources are the
Phase 6 skill and the Phase 6 MCP server capability
descriptor.

The packager emits:

```text
dist/claude-code/
├── .claude-plugin/
│   └── plugin.json
├── .mcp.json
├── skills/
│   └── project-intelligence/
│       ├── SKILL.md
│       └── references/...
├── commands/        # optional
├── agents/          # optional
└── README.md
```

The plugin slug MUST be treated as stable after public
release. The packager is deterministic (skill content
hash); two consecutive runs with the same canonical
sources MUST produce byte-identical artifacts.



### Requirement: claude-code-packager is generated, not maintained

The Claude Code plugin package MUST be generated by a
code packager from the canonical sources. The package
MUST NOT be maintained by hand; the canonical sources
are the Phase 6 Agent Skill and the Phase 6 MCP server
capability descriptor.

#### Scenario: packager regenerates the bundle

Given the canonical Agent Skill at
`distribution/skills/project-intelligence/SKILL.md` is
updated
When the packager runs
Then `dist/claude-code/` is regenerated
And the bundled `SKILL.md` is byte-identical to the
canonical `SKILL.md`.

### Requirement: claude-code plugin manifest schema

The Claude Code plugin manifest MUST be emitted at
`dist/claude-code/.claude-plugin/plugin.json` and MUST
declare the documented fields. The packager MUST emit
the manifest with every documented key and MUST
validate the manifest against the documented JSON
schema at packaging time. The documented fields are:

- `name` — the canonical plugin name
  (`project-intelligence`);
- `version` — the semver plugin version, aligned with
  the canonical skill version;
- `mcp` — the MCP server endpoint (local stdio path
  or HTTP URL);
- `skill` — the bundled skill's name, version, SHA-256
  content hash and `mcp-api` semver range;
- `license` — the plugin license (Apache-2.0);
- `assets` — the list of bundled assets.

#### Scenario: plugin manifest carries the documented fields

Given the packager runs with the canonical skill at
version `1.4.0`
When the operator reads
`dist/claude-code/.claude-plugin/plugin.json`
Then the manifest declares the documented fields
And `skill.sha256` matches the canonical `SKILL.md`
content hash.

### Requirement: claude-code MCP configuration

The packager MUST emit `dist/claude-code/.mcp.json`
pointing to the local or remote Project Intelligence
MCP endpoint. The MCP configuration MUST carry the
`mcpApiVersion` and the supported semver range.

#### Scenario: mcp.json points to the documented endpoint

Given the packager runs with the default
configuration
When the operator reads
`dist/claude-code/.mcp.json`
Then the file carries the `mcpApiVersion` and the
supported semver range
And the endpoint matches the documented transport (default
stdio, optional HTTP).

### Requirement: marketplace-ready metadata

The packager MUST emit marketplace-ready metadata so
the plugin can be distributed through a marketplace
when desired. The metadata MUST include the plugin
name, version, license, the canonical repository URL
and a one-paragraph description of the integration.

#### Scenario: marketplace metadata is present

Given the packager runs
When the operator inspects the plugin manifest
Then the marketplace fields are present
And the metadata is non-redundant with the manifest's
other fields.

### Requirement: stable plugin slug

The plugin slug (`project-intelligence`) MUST be
treated as stable after public release. The packager
MUST NOT rename the slug without a documented
migration plan; the slug is the public identifier the
marketplace uses.

#### Scenario: plugin slug is stable

Given the plugin is published
When the operator inspects the plugin manifest
Then `name` is `project-intelligence`
And no rename is documented.

### Requirement: optional commands and agents

The packager MUST emit `commands/` and `agents/`
directories only when the canonical sources ship
command / agent content. When emitted, the directories
MUST contain Claude Code command and agent files the
plugin marketplace can register. The commands and
agents MUST delegate to the MCP server; they MUST NOT
duplicate business / retrieval rules.

#### Scenario: commands delegate to the MCP server

Given the packager emits a `commands/` directory
When the operator inspects a command file
Then the command delegates to the MCP server
And the command does NOT contain retrieval logic
itself.

### Requirement: deterministic build

The packager MUST be deterministic. Two consecutive
runs with the same canonical sources MUST produce
byte-identical artifacts. The determinism MUST be
verified across the complete output file tree with fixed build inputs; the plugin
manifest MUST include the skill SHA-256 so two runs
with the same skill content produce the same manifest.

#### Scenario: two runs produce identical artifacts

Given the canonical sources are unchanged
When the packager runs twice consecutively
Then the byte sequence of
`dist/claude-code/.claude-plugin/plugin.json`,
`dist/claude-code/.mcp.json`, the bundled `SKILL.md`
and the optional `commands/` and `agents/` are
identical.

### Requirement: README documents the plugin

The packager MUST emit a `dist/claude-code/README.md`
that documents the integration. The README MUST cover
the plugin name, version, license, MCP endpoint, skill
content hash and the documented commands / agents.

#### Scenario: README documents the integration

Given the packager runs
When the operator reads `dist/claude-code/README.md`
Then the README carries the documented fields
And the content is non-empty and consistent with the
plugin manifest.
