# opencode-plugin-package Specification delta

Covers architecture section §43 (OpenCode Plugin
Distribution Profile) and §45 (Plugin Generation
Pipeline). The OpenCode plugin package emits a package
that OpenCode can install either as a published npm
package or as a local project plugin. The package is
generated, NOT maintained by hand; the canonical sources
are the Phase 6 Agent Skill and the Phase 6 MCP server
capability descriptor.

The packager emits:

```text
dist/opencode/
├── package.json
├── plugin/
│   └── project-intelligence.ts
├── skill/
│   └── project-intelligence/
│       └── SKILL.md
├── config/
│   └── opencode.example.jsonc
└── README.md
```

OpenCode supports both MCP server configuration and
JavaScript / TypeScript plugins; the package exposes a
TypeScript or JavaScript plugin adapter that delegates
to the MCP server. The plugin adapter MUST NOT own
retrieval / business rules; all knowledge / retrieval
logic remains in the Project Intelligence core.

## ADDED Requirements

### Requirement: opencode-package is generated, not maintained

The OpenCode plugin package MUST be generated by a code
packager from the canonical sources. The package MUST
NOT be maintained by hand; the canonical sources are
the Phase 6 Agent Skill and the Phase 6 MCP server
capability descriptor.

#### Scenario: packager regenerates the bundle

Given the canonical Agent Skill at
`distribution/skills/project-intelligence/SKILL.md` is
updated
When the packager runs
Then `dist/opencode/` is regenerated
And the bundled `SKILL.md` is byte-identical to the
canonical `SKILL.md`.

### Requirement: opencode package manifest schema

The OpenCode package manifest MUST be emitted at
`dist/opencode/package.json` and MUST declare the
documented fields. The packager MUST emit the manifest
with every documented key and MUST validate the
manifest against the documented JSON schema at
packaging time. The documented fields are:

- `name` — the canonical npm package name
  (`@project-intelligence/opencode`);
- `version` — the semver package version, aligned
  with the canonical skill version;
- `mcp` — the MCP server endpoint (local stdio path
  or HTTP URL);
- `skill` — the bundled skill's name, version,
  SHA-256 content hash and `mcp-api` semver range;
- `license` — the plugin license (Apache-2.0);
- `opencode` — the OpenCode plugin entry point.

#### Scenario: package manifest carries the documented fields

Given the packager runs with the canonical skill at
version `1.4.0`
When the operator reads `dist/opencode/package.json`
Then the manifest declares the documented fields
And `skill.sha256` matches the canonical `SKILL.md`
content hash.

### Requirement: typescript or javascript plugin adapter

The packager MUST emit a TypeScript or JavaScript
plugin adapter under `dist/opencode/plugin/`. The
adapter MUST delegate to the MCP server and MUST NOT
own retrieval / business rules. The adapter MUST use
the documented OpenCode plugin API; the adapter MUST
be optional — when OpenCode ships the skill convention
natively the packager may skip the adapter.

#### Scenario: adapter delegates to MCP

Given the packager runs and OpenCode does not yet
support the skill convention natively
When the operator inspects the adapter
Then the adapter delegates to the MCP server
And the adapter does NOT contain retrieval logic
itself.

### Requirement: bundled skill for opencode

The packager MUST emit
`dist/opencode/skill/project-intelligence/SKILL.md` as
a snapshot of the canonical Agent Skill. The bundled
`SKILL.md` MUST be byte-identical to the canonical
`distribution/skills/project-intelligence/SKILL.md`.

#### Scenario: bundled SKILL.md matches canonical

Given the packager runs
When the operator diffs the bundled `SKILL.md` against
the canonical file
Then the two files are byte-identical
And the SHA-256 of the bundled file matches the
canonical content hash.

### Requirement: opencode.example.jsonc configuration

The packager MUST emit
`dist/opencode/config/opencode.example.jsonc` as a
reference OpenCode configuration that registers the MCP
project's endpoint. The example MUST carry the documented
fields:

- `mcp.servers` — the documented MCP server entry
  pointing to the local or remote endpoint;
- `mcp.servers.<name>.command` — the stdio launch
  command;
- `mcp.servers.<name>.env` — the optional environment
  variables.

#### Scenario: example configuration is reference-only

Given the packager runs
When the operator inspects
`dist/opencode/config/opencode.example.jsonc`
Then the file is marked as a reference example
And it carries the documented fields.

### Requirement: deterministic build

The packager MUST be deterministic. Two consecutive
runs with the same canonical sources MUST produce
byte-identical artifacts. The determinism MUST be
enforced through the skill content hash; the
`package.json` MUST include the skill SHA-256 so two
runs with the same skill content produce the same
manifest.

#### Scenario: two runs produce identical artifacts

Given the canonical sources are unchanged
When the packager runs twice consecutively
Then the byte sequence of `dist/opencode/package.json`,
the plugin adapter, the bundled `SKILL.md`,
`config/opencode.example.jsonc` and `README.md` are
identical.

### Requirement: npm-publishable OR local-project-usable

The OpenCode package MUST be publishable as a versioned
npm package OR usable as a local project plugin. The
packager MUST emit the package under a directory that
satisfies the npm tarball layout. The `package.json`
MUST declare a `main` or `exports` entry that OpenCode
can resolve.

#### Scenario: package resolves as a local plugin

Given the packager runs and the package is consumed as
a local project plugin
When OpenCode loads the package
Then the `package.json` `main` or `exports` entry
resolves successfully
And the MCP server is registered through the
documented configuration.
