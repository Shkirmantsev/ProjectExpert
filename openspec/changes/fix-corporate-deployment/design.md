## Implemented

The Windows launcher keeps the selected Docker context. The base Compose
configuration leaves engine-provided DNS intact. One production-image helper
tries the two engine host aliases and a bounded list of Windows WSL/Docker
virtual-interface addresses. It ignores inherited HTTP proxy variables and
rejects redirects. It first issues an unauthenticated request, then verifies the
managed credential, pinned model alias and a finite 768-component synthetic
embedding before passing the numeric route to production. The helper emits
stage codes for DNS, refusal, authorization and model errors. No project text
participates in discovery. Linux Docker Engine retains its host alias through
a Linux launcher overlay; WSL launchers leave desktop DNS alone.

The selected port reaches the native argv, container probe, profile
benchmarks, managed argv, managed health check, and application endpoint. The
managed sidecar can omit the embedding API key only when explicitly configured.
It publishes no host port and retains a separate authenticated control request
path. Native Windows authentication stays managed. Restarting with a changed
native port requires stopping the kit-owned process first.

An explicit Windows connect command resolves the active local Docker named
pipe context and reads the native listening socket. The operator can supply a
token file mounted read-only, reuse the kit key, or choose tokenless operation.
Tokenless mode requires that all listening bindings on the port are private
WSL/Docker interfaces or loopback, with an actual bridge binding and a single
listener owner. Docker tests the selected Windows bridge address, model and
embedding payload. The launcher rechecks listener ownership after the smoke
and records the selected route without creating process-ownership state.
This attach path deliberately reports the manually selected runtime's GPU
mode as unknown until it has direct device evidence.

GPU preparation reuses verified asset pins, the existing offline verifier and
the isolated native installation. The Windows CUDA installer selects a
preapproved pack for future startup through private state after verification.
Windows Vulkan stages verified bundled assets. Linux prepares the pinned
runtime image. Host display drivers, device passthrough, employer license
approval and Docker daemon trust are prerequisites outside this operation.

The private source-stage report is atomic, records the job identity, attempted
counts, relative source paths, hashes, parser family, stage and category, and
omits source text or raw exception messages. It is diagnostic evidence for the
source pass. It is not an active generation or a statement about embedding
success. The encoding form writes the existing private policy via its protected API.

Strict indexing remains the default. The explicit local partial policy permits
isolated source failures, records coverage in the fenced SQLite job, validates
the candidate artifacts, and exposes coverage through indexing status. Local
search and MCP can use the successful portion. Git export checks the published
source stage and requires zero skipped sources. Model, cancellation,
configuration, and integrity errors still block publication.

## Remaining design and acceptance sequence

1. Bring organizational CUDA review into a guided recorded transaction for
   the exact closure. Keep redistribution approval independent. Diagnose
   registry TLS at the effective daemon and validate actual pulls with the
   organization-approved root. Retain the existing separate host CA runtime
   bundle, strict TLS and no persistent setup container.
2. Extend the source error classification to distinguish optional parser-family
   outages from individual file failures. Provide explicit partial coverage
   metadata to MCP clients and guard mixed-version readers.
3. Exercise interrupted builds, invalid assets, changed branches, missing
   vectors, corrupt SQLite, and repair from partial to complete. Verify
   exact paired image and kit digests on Windows Docker Desktop, Windows
   Rancher Desktop and Linux Docker with the actual corporate repository, its
   proxy, and supported physical GPUs. Record indexing and warm reuse timings
   and confirm no extra persistent services.
