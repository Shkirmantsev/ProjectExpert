# v0.8 §68 Architectural Invariants

The v0.8 architecture document (`project-intelligence-platform-architecture-v0.8.md`)
records **52 architectural invariants** in §68. Phase 10 ships a
probe class for every invariant, but not all probes are equally
binding — see [Enforcement split](#enforcement-split) below.

The probes live in `tests/test_phase_10_invariants.py`. The loader
in `pi_platform/core/eval/invariants.py` (`discover_probes`,
`INVARIANT_COUNT = 52`) is the source of truth for the count.

## Enforcement split

As of the Phase 10 close-out the 52 probes split into two classes:

- **enforced (52)** — every probe body returns a value that
  depends on observed platform state, so it can fail. The
  classifier is conservative: a probe with dead-code
  assignments and a literal `return (True, ...)` is classified
  `declared`, not `enforced`. The adversarial suite in
  `tests/test_phase_10_adversarial.py` breaks each probe in
  turn to prove the verdict can actually flip.
- **declared (0)** — none remain. All 52 §68 probes have a real
  check, and the gate's `52/52` line genuinely means 52 enforced
  acceptance checks.

`make invariants` reports both counts (`invariants_enforced`,
`invariants_declared`) alongside `invariants_run` /
`invariants_passed`. The classification is derived in
`pi_platform/core/eval/runner.py::classify_probe` by AST inspection of
the probe body and is conservative: anything unreadable or ambiguous
is reported as `declared`, so the gate never overstates coverage.

Closing the 0 `declared` probes into real checks is open work; the
52/52 line in `make invariants` now genuinely means 52 enforced
acceptance checks. The adversarial suite
(`tests/test_phase_10_adversarial.py`) breaks each probe in turn
to prove the verdict can actually flip.

## Running the suite

```text
make invariants
# or
python -m pi_platform.cli invariants
# or
python -m unittest tests.test_phase_10_invariants
```

The command exits non-zero when any probe fails **or** when the
suite fails. The report includes the invariant id, the label and the
failure detail, plus the enforced/declared split. Both `eval` and
`invariants` atomically rewrite
`tmp/local/project-context/eval/last.json`; `make metrics-gate` then
validates that file against the documented bounds.

## Adding or retiring an invariant

Adding or retiring an invariant requires three coordinated
changes:

1. Update the architecture document (§68) and reference this
   node from the change.
2. Update `INVARIANT_COUNT` and add or remove a probe class in
   `tests/test_phase_10_invariants.py`.
3. Update this table.

A follow-up ADR records the rationale and links the change.
