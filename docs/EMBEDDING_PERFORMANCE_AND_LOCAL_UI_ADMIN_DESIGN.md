# ProjectExpert · Продуктивність індексації та локальне адміністрування UI

**Проєкт рішення для обговорення та реалізації · 23 листопада 2026 року**

Для робочого ПК з NVIDIA MX550 та Intel Iris Xe пропоную спочатку усунути зайву роботу на шляху від готового фрагмента до збереженого пошукового індексу. Після цього можна достовірно виміряти, що додає другий GPU. Окрему зміну варто випустити для локального UI: оператор відкриває звичну адресу на localhost і працює без введення токена, навіть коли Rancher Desktop переадресовує з’єднання з іншої IP-адреси.

Документ уточнює наданий *ProjectExpert — Embedding throughput and tokenless local UI administration*. Початковий звіт посилається на ревізію `8279eaaa`. Код і локальні експерименти нижче перевірено на `ddd3092`. Для обох ревізій GitHub повернув порожній список змінених файлів при порівнянні. Дані робочого ПК взято з вкладення. Оригінальних трасувань, корпоративного корпусу й фізичних GPU цього ПК в цій перевірці не було. ## 1. Де витрачається час

У звіті описано 14 457 файлів і близько 106 372 фрагментів. За 28 хвилин оброблено 4 736 фрагментів, тобто 2,82 фрагмента/с. За сталих 2,8/с весь етап тривав би близько 10 год 33 хв. Під час нового запуску `nvidia-smi` показував 92–100% використання MX550 і 923 MiB зайнятої пам’яті. Це свідчення роботи CUDA у спостережуваний період. ## 2. Як виміряти й прийняти прискорення

**Основне порівняння** — час від входу в етап ембедингів до готового, збереженого й перевіреного векторного індексу для того самого набору фрагментів. Для холодного тесту швидкість дорівнює кількості унікальних нових фрагментів, для яких зафіксовано валідний вектор, поділеній на цей час. Окремо звітувати про тривалість всього запуску до готовності пошуку, час обчислення на пристрої, побудову ANN, активацію, кількість імпортованих і повторно використаних векторів. Для теплого запуску основний показник — час до готовності, навіть якщо нових векторів нуль.

1. Зафіксувати версії застосунку, комплекту й образів, модель, профіль, драйвер, ідентифікатори пристроїв, конфігурацію WSL/контейнера і живлення. Тестувати на ізольованій локальній копії стану з тим самим початковим кешем. Кожен варіант отримує власний робочий кеш. Дослід не повинен змагатися з активною індексацією за GPU.
2. Взяти відтворювану вибірку з реального розподілу мов, довжин, Java/SQL, документів і кількості сегментів. Зафіксувати відбиток вибірки й лічильники без запису її тексту в діагностику. Виміряти окремо текст і медіа. Для первинного відбору достатньо 200–500 фрагментів. Для сталого темпу використати щонайменше 2 000–5 000, прогріти пристрої та виконати щонайменше три повтори кожного фінального варіанта, чергуючи порядок.
3. Порівняти старий і новий код на одному MX550, далі окремо Iris Xe і CPU, потім сумісні комбінації. Включити CPU як додаткового виконавця лише за виграшу в сумарному вимірі. Повторити з паралельними пошуковими запитами. Перевірити фінальну конфігурацію на всьому корпусі за однакового охоплення джерел.
4. Показати всі повтори й медіану. Для змішаного режиму зберегти наявну сувору умову: найгірший повтор комбінації швидший за найкращий окремий результат учасників. Для заяви про **3× на робочому ПК** потрібні щонайменше триразове скорочення медіанного часу етапу проти контрольного старого запуску і контроль повного корпусу. **8,4 фрагмента/с** — орієнтир від повідомлених 2,8/с, або близько 3 год 31 хв на етап. Якщо межу не досягнуто, вказати виміряний виграш та етап, що обмежує швидкість.
5. Опублікувати разом із результатом p50/p95 затримки пошуку, найвище використання RAM/VRAM, кількість помилок, охоплення і результати перевірки пошуку. Початкова запропонована межа для порівняння конфігурацій — p95 інтерактивного пошуку під час індексації до 110% від контрольного p95 за такого самого потоку запитів. Узгодити межу до замірів.

У вкладенні короткі пакети дали до 6,8 фрагмента/с на MX550 і 4,8/с на Iris Xe в окремих експериментах за одночасної виробничої роботи. Ці числа не можна додавати для прогнозу. Високе використання CUDA означає, що прискорення лише за рахунок зменшення пауз CPU може виявитися обмеженим. Якщо контроль показує насичений GPU і малу частку запису, наступний дослід — кількість корисних токенів за секунду та незалежна робота iGPU.

## 3. Обчислення, запис і відновлення

| Черга реалізації | Контракт | Коли етап готовий |
|---|---|---|
| 1. Таймери та раннє повернення | Додати в наявний API стану час пошуку в кеші, підготовки, виклику моделі, запису SQLite, побудови ANN й активації. Успішно завантажене покоління повертає повний `IndexingReport` із чинними полями. Перед поверненням перевірити профіль, унікальну множину ID і хешів тексту/проєкції, записи SQLite, розмірність, ключі sidecar, відповідність native-індексу та поточні метадані фрагментів. | Тепле відновлення робить нуль викликів моделі для документів і нуль змін ANN, повертає ті самі результати з тими самими джерелами. Пошкоджений ANN перебудовується з перевірених векторів. Відсутні вектори в режимі «лише відновлення» дають наявний результат «потрібна переіндексація». |
| 2. Пакетна побудова ANN | SQLite залишається джерелом векторів. Використати наявні `get_many`/`put_many`. Окремо будувати покоління-кандидат із зафіксованих записів. Виділяти стабільні числові ключі транзакцією на пакет, додавати валідовані матриці пакетами. Писати карту ключів і метадані на межі покоління, сумісний покажчик оновлювати під час успішної публікації. | Кількість записів метаданих залежить від кількості поколінь/контрольних точок. Поточне покоління можна читати протягом побудови. Збій диска, записувача або процесу залишає попередній індекс доступним. |
| 3. Підготовка і HTTP | Оцінювати **готовий** текст після застосування ролі, заголовка та спеціальних токенів. Перевірити відповідність локального токенізатора закріпленій моделі через наявний `/tokenize` на граничних довжинах, кирилиці й коді. До підтвердження використовувати чинну консервативну стратегію. Обмежити кількість елементів, токенів на послідовність і пакет, байтів запиту й відповіді. | Граничні запити приймаються або дають пояснену помилку. Розбиття пакета дозволене для підтвердженої помилки місткості. Сьогодні 400/413/422 потрапляють в одну категорію. Невалідний формат, модель, ключ або запит не повинні викликати каскаду повторів. |
| 4. Безперервна подача | Один диспетчер на етап. Один власник моделі на виконавця. Обмежена черга пропусків кешу → сумісні виконавці → обмежена черга результатів → один власник запису. Швидший пристрій забирає наступний вільний пакет. Записувач обробляє готові результати без очікування повільнішого пристрою. | Два реальні пристрої одночасно обробляють незалежні пакети, зокрема за високої частки влучань у кеш. Пам’ять обмежена також для довгих PDF. Скасування або помилка записувача завершує всі черги й звільняє ресурси. |

**Межа пам’яті.** Глобальний ліміт має охоплювати підготовлені запити, запити в польоті, відповіді та сегменти, що чекають на збирання. Вводити ліміт у байтах поряд із кількістю завдань. Для великого PDF видавати сегменти поступово, залишати записувачу ресурс для завершення вже розпочатого фрагмента. Не резервувати всю чергу для незавершених документів. За 106 372 векторів по 512 компонентів тільки щільні значення float32 займають близько 208 MiB. Виміряти RSS до вилучення повних копій у Python і перевірити окремо native та тестовий точний пошук.

**Транзакції та порядок.** Зв’язувати результат із поколінням завдання, ID фрагмента, хешем фактичного вводу, профілем, порядковим номером і кількістю сегментів. Відкидати застарілі результати після скасування чи зміни гілки. Для PDF відтворити поточне впорядковане усереднення і нормалізацію. Рахувати завершення фрагмента після успішного commit усіх потрібних даних. Після збою між commit і контрольним записом звірятись із SQLite. З’єднання з SQLite, зокрема `DenseKeyStore`, створює і закриває його потік-власник. Мережеві виклики виконуються поза транзакціями.

**Цілісність покоління.** Число векторів саме по собі не виявляє переставлених ID. Вузол публікації перевіряє зв’язок між ID, ключем ANN, профілем і хешем вводу, контрольні суми файлів кандидата, вибірковий пошук та актуальну версію джерел. Якщо після зміни фільтрів чи прав змінилися тільки метадані, оновити їх перед видачею результатів. Перевірити паралельне читання старого покоління під час запису нового. Зберегти сумісність читання попереднього формату. Для bulk API USearch спершу перевірити встановлену версію, порядок ключів, їх унікальність і поведінку при частковій помилці.

**Додаткові оптимізації після замірів.** Для повторів згенерованого коду спершу порахувати збіги точного форматованого вводу. Міжфрагментний кеш має сенс за суттєвої частки збігів і лише всередині того самого приватного проєкту, з урахуванням ролі, моделі, профілю, проєкції та хешів медіа. Кожен фрагмент зберігає власний ID, джерело та класифікацію. Профілювати JSON, читання файла ключа й створення HTTP-клієнта перед зміною транспорту. При повторному використанні з’єднань зберегти межі відповідей, тайм-аути, ротацію ключа, TLS і чинну політику проксі. ## 4. Вибір пристроїв у звичайному запуску

Спільний механізм вибору виконавців має читати перевірений план для запуску через Make, CLI, майстер UI та фонове завдання переіндексації. Поточні налаштування одного бекенда й ручний вибір оператора мають пріоритет. За відсутності придатної калібровки Auto запускає вже перевірений одиночний маршрут. Повну калібровку запускати окремою операцією за наявності вільних ресурсів. Запропоновані цілі Make — `platform-embedding-benchmark` і `platform-embedding-status`; звичайному користувачу для старту вони не потрібні.

| Середовище | Кандидати та умови допуску |
|---|---|
| Windows, Rancher Desktop / WSL2 | MX550 через підтверджений CUDA passthrough або native Windows. Iris Xe через native Vulkan, якщо контейнер його не бачить. Перевірити маршрут **з контейнера застосунку** реальним запитом до моделі. Окремі керовані процеси, порти, файли ідентичності, ключі та журнали для кожного виконавця. |
| Linux | Перевірити CUDA з доступом контейнера до NVIDIA і Vulkan з доступом до відповідного render node у `/dev/dri`. Перевірити права, завантаження закріпленої моделі й фактичний обчислювальний запит. CPU доступний як самостійний маршрут. Драйвер на хості сам по собі не підтверджує доступ із контейнера. |
| Спільні ресурси | Зіставити стабільний апаратний ідентифікатор через UUID/LUID/PCI або перевірену відповідність render node. CUDA0 та Vulkan0 можуть бути одним GPU. При неоднозначній відповідності залишити один маршрут. Виключити програмний Vulkan. CPU й iGPU ділять RAM, пропускну здатність і термічний бюджет. Для CPU врахувати ліміт WSL/cgroup, потоки бекендів, записувача, ANN та інтерактивний пошук. |

План додає до сумісних полів версії 2 окремі маршрут запитів і набір маршрутів документів. Записує ідентичності обладнання, runtime й моделі, аргументи запуску, обмеження пам’яті та відбиток калібровки атомарно. Зміна драйвера, моделі, фізичного пристрою, доступної пам’яті або лімітів пакета потребує повторної перевірки. Секрети зберігати окремо. Повторне використання перевіреного плану не повинно затримувати кожен старт повним бенчмарком. Суворий явно вибраний GPU зберігає чинну поведінку при недоступності.

Для проб почати з чинних значень 4096 та одного слота. Для Iris Xe окремо випробувати micro-batch 512 і 1024, для MX550 — один та кілька слотів у межах 2 GB VRAM. Вибирати за виміром з документами реальної довжини. Поточна прийнята специфікація визначає сумісні типові ліміти 4096 для обох способів запуску. Нові автоматично підібрані значення потребують явно погодженої зміни OpenSpec перед увімкненням за замовчуванням. [Чинні вимоги середовища виконання](https://github.com/Shkirmantsev/ProjectExpert/blob/ddd3092284193465cf7f49650be18f482c53eb00/openspec/specs/2026-10-25-portable-inference-runtime/spec.md)

**Якість і відмови.** Допускати змішані текстові обчислення за однакового профілю, ролі, токенізатора, вимірності, нормалізації та перевірки ідентичності до й після запиту. Утримати чинні пороги для репрезентативних даних — cosine ≥ 0,999, максимальна абсолютна різниця компонентів ≤ 0,01, однакові top-k для кожного пристрою та комбінації. Додатково перевірити результати виробничого ANN/гібридного пошуку, оскільки порядок вставки здатний змінити граф навіть при однакових векторах. Текстова перевірка не дає допуску для медіа. Маршрутизувати їх і запити пошуку за окремими перевіреними можливостями. Інтерактивним запитам надати пріоритет на межі пакета й обмежити їхній час у черзі.

Якщо виконавець зникає, припинити видачу нових пакетів цьому пристрою. Повторювати тільки незавершені завдання на сумісному пристрої, з обмеженням кількості спроб і часу. Оновлювати стан пристрою та причину деградації. Якщо можливостей не вистачає, зберегти підтверджену роботу та завершити завдання з діагностикою. Правило пропуску окремих файлів стосується джерел. Його не можна поширювати на втрачені відповіді моделі, неповні вектори або збій сховища. Зберегти доступність попереднього опублікованого покоління.

## 5. Локальний UI без ручного токена

**Симптом, який треба усунути.** На робочому ПК сторінка відкрилася через localhost, але збереження параметрів обміну повернуло HTTP 403. До виправлення сервер усередині контейнера перевіряв адресу TCP-клієнта за loopback і шлюзом із `/proc/net/route`. Rancher Desktop може показати іншу адресу переадресації. Водночас `/api/v1/auth-status` повідомляв про локальні права за налаштуванням сервера, тому UI може пропонувати дію, яку сервер відхилить. У Compose є також окремий Open WebUI, що звертається до застосунку внутрішньою мережею. Тож однієї перевірки публікації порту на localhost недостатньо для надання всім запитам у контейнері прав адміністратора. [HTTP-сервер](https://github.com/Shkirmantsev/ProjectExpert/blob/ddd3092284193465cf7f49650be18f482c53eb00/pi_platform/adapters/ui/http_server.py) · [Мережа комплекту](https://github.com/Shkirmantsev/ProjectExpert/blob/ddd3092284193465cf7f49650be18f482c53eb00/distribution/deployment/compose.yaml)

| Значення `PI_UI_TOKEN` у запущеному контейнері | Поведінка UI |
|---|---|
| Змінна відсутня або порожня | Звичайна адреса сервісу відкриває всі можливості адміністратора як локальному, так і віддаленому користувачеві. Поле токена приховане. |
| Задано токен | UI показує форму входу. API повертає HTTP 401 для запитів без bearer або з неправильним значенням. |
| Лише пробільні символи | Запуск повідомляє про помилкову конфігурацію. |

`PI_BIND_HOST` керує доступністю сервісу в мережі окремо від входу. За
замовчуванням використовується loopback. У режимі без токена будь-хто, хто
може підключитися до адреси сервісу, отримує адміністративний доступ.
`platform-open` відкриває звичайну адресу з фактичного порту Compose. Після
додавання чи вилучення змінної контейнер потрібно перестворити.

HTTP-статус доступу і маршрути адміністратора використовують однакове рішення.
Для браузерних записів без токена сервер перевіряє Origin і Fetch-Site.
Підписані дозволи на публікацію, перевірка отриманої пропозиції, фільтри
конфіденційності та політика вихідних з’єднань застосовуються окремо.

## 6. Довгі шляхи, збої парсингу та стан індексації

- **Встановлення на Windows.** Раніше абсолютний шлях містив корінь комплекту, 64 символи digest, суфікс staging з GUID і внутрішні каталоги архіву. У вкладенні повідомлено про шляхи до 325 символів під час розпакування. Використати короткий приватний корінь кешу користувача і короткий тимчасовий каталог на тому самому томі. Повний SHA-256 залишається ідентичністю пакета та перевіряється перед використанням. Коротка назва каталогу сама не підтверджує його вміст. Перед розпакуванням перевіряти найдовший внутрішній шлях, доступ і вільне місце для старого й нового пакета. Перехід виконувати під блокуванням із атомарною заміною покажчика після перевірки. Перевірений старий пакет можна повторно використати або перенести без повторного завантаження. Після збою прибирати лише staging, яким володіє ця інсталяція. Окремі коди помилок для шляху, браку місця, digest, завантаження бібліотеки, драйвера та маршруту з контейнера. Перевірити fresh/upgrade/repair/stop із довгого каталогу через PowerShell 5.1 і 7, також після перерваного розпакування. [Наявний Windows-інсталятор](https://github.com/Shkirmantsev/ProjectExpert/blob/ddd3092284193465cf7f49650be18f482c53eb00/distribution/deployment/setup-windows-accelerator.ps1)
- **Парсинг.** У вкладенні повідомлено про 13 невдалих джерел і 1 045 оброблених з обмеженнями, переважно для згенерованої Java, включно з аварійним завершенням парсера. Первинну причину SIGSEGV ще слід відтворити на дозволеному мінімальному прикладі з фіксованою версією парсера. Фіксувати сімейство файлів, версію й код завершення, використовувати ізоляцію процесу й наявний запасний розбір за його контрактом. Показувати окремо пропущені, деградовані та успішні джерела. Повторювати проблемні файли після зміни джерела, парсера чи правил повтору. При корпоративному кодуванні зберегти автоматичне читання CP1251. Вимірювати швидкість на незмінному охопленні.
- **Видимий прогрес.** Розширити чинний `GET /api/v1/indexing-status`. Для етапу показувати підготовлені фрагменти, пропуски кешу, кількість обчислених сегментів, **записані фрагменти**, побудову ANN і стан публікації. Для пристрою розрізняти «виявлено», «перевірено», «обробляє пакет», «очікує запису» й «недоступний». Показувати швидкість за рухомим вікном, час останнього успіху й причину повтору. ETA рахувати за стійким темпом збереження, для ANN показувати окрему оцінку або «ще немає даних». Якщо черги порожні, а етап не завершився, показати умову очікування та застосувати дедлайн відповідної операції. Лічильник у 100% для векторів ще не означає готовності пошуку. У UI достатньо показати поточний етап, прогрес і причину очікування, детальні метрики відкрити в діагностиці.
